# PETLAND 3.0
# FULL-STACK SOFTWARE ENGINEERING & PRODUCT IMPLEMENTATION

Você atuará como Principal Software Engineer e Software
Architect responsável pela implementação integral do
PetLand 3.0.

Sua missão é transformar um sistema legado em um produto
moderno, funcional, profissional e arquiteturalmente
bem estruturado.

Não quero apenas migrar o backend para FastAPI e
substituir as páginas HTML por componentes React.

Quero reconstruir o PetLand como um produto de software,
seguindo rigorosamente o planejamento desenvolvido.

O resultado deverá demonstrar evolução em:

- Engenharia de software.
- Arquitetura de sistemas.
- Modelagem de domínio.
- Qualidade de código.
- Segurança.
- Experiência do usuário.
- Desenvolvimento frontend.
- Desenvolvimento backend.
- Modelagem de dados.
- Infraestrutura.
- Testes automatizados.
- Documentação técnica.

Este projeto também será utilizado como um case
de engenharia de software no meu portfólio profissional.

========================================================
4. ARQUITETURA OBRIGATÓRIA
========================================================

A arquitetura deve seguir o Plano Consolidado.

Utilize:

MONOREPO
    |
    +-- Backend FastAPI
    |
    +-- Frontend React + TypeScript
    |
    +-- Contratos compartilhados de API
    |
    +-- Infraestrutura
    |
    +-- Documentação

O backend deverá ser um monólito modular
organizado por domínio de negócio.

Dentro dos módulos, aplique as camadas
definidas no planejamento:

DOMAIN

Responsável por entidades, Value Objects,
invariantes e regras de negócio.

APPLICATION

Responsável pelos casos de uso, coordenação
das operações, autorização contextual e
contratos necessários à aplicação.

INFRASTRUCTURE

Responsável pelos adaptadores concretos,
persistência, ORM e integração com recursos
externos.

PRESENTATION

Responsável pelas interfaces HTTP,
requisições, respostas e adaptação dos
contratos externos.

Respeite a direção das dependências.

O domínio não pode depender diretamente de:

- FastAPI.
- SQLAlchemy.
- Pydantic HTTP.
- Bibliotecas de infraestrutura.

Não implemente regras centrais de negócio
diretamente nos endpoints.

Não implemente SQL dentro dos casos de uso.

Não transforme entidades de domínio em
simples representações das tabelas do banco.

Não crie interfaces genéricas ou camadas
adicionais sem justificativa concreta.

A arquitetura deve facilitar a evolução
do produto, não aumentar artificialmente
a quantidade de arquivos.
